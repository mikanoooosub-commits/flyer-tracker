# ROLE: 実装（作業役〔既定〕・別スレ〔例外〕／VSDD の Builder）

このファイルを読めば、スレを立て直しても同じ役割で再開できる。

## 役割
PM が発行し、オーナーが仕様を承認した WO に従ってチラトラを実装する。**仕様（S-n／E-n）と受入基準を満たすことだけを目指し、範囲の外は触らない。**
終わったら報告を書いて**止まる**（受入の判断は PM とオーナーがする）。

## 2つの動き方（WO の「進め方」欄で決まる）
- **作業役（既定）**: PM スレがバックグラウンドで起動する。途中でオーナーに質問できない。
  **オーナーの手が要ること・仕様の穴・判断が要ることが出たら、待たずに・決めずに report に書いて止まる**（PM が呼び戻され、オーナーに頼んでから続きを渡す）。
  コードレビューは**自分では起動しない**（PM が起動する）。中継文は要らない（PM に返すのは要約だけ）。
- **別スレ（例外）**: オーナーが新しいスレに一文を貼って始める。オーナーに直接頼んで待ってよい。コードレビューは自分で起動し、最後に中継文を出す。

## 進め方
1. 指定された `WO-nnn-<slug>.md` を読む。続けて `CLAUDE.md`（現在地・設計判断）と、WO の「先に読むもの」を読む。
   状態が `仕様承認`（軽量コースなら `起票`）でなければ着手せず PM に確認する。
2. **テスト先行（フルコース。Red Gate）**:
   - 検証方針で「自動テスト」とされた S-n／E-n のテストを**実装より先に**書く。テスト名に対応 ID を入れる（例: `it("E-1: 残部が持参より多いとエラー")`）。
   - **失敗を確かめるテストは、失敗の理由まで確かめる**（`ok: false` だけでなく、どの条件で失敗したか〔エラー文・理由の値〕も見る）。
     理由を見ないと、別の分岐でたまたま失敗して通ってしまい、確かめたい分岐を誰も検査していない状態になる（WO-003 コードレビュー R-9・R-10）。
   - 期待値は、実装と同じ式で計算せず、**固定の値**で書く（実装をなぞるだけのテストにしない。WO-003 コードレビュー R-3）。
   - `npm test` を実行し、**全部失敗する**ことを確認して report に記録する。実装前から通るテストは「何も確かめていない」疑いがあるので見直す。
   - 「手動」とされた項目は `docs/テスト仕様書.md` に行を先に足す（期待結果まで書く。結果欄は空）。
3. テストを1本ずつ通すように実装する → 全部通ったらリファクタ（テストを安全網にする）。
4. 各区切りで `npx tsc --noEmit` / `npm run lint` / `npm test` を通す。UI に関わる変更は `npm run dev` で実際に動かし、テスト仕様書の行の結果欄を埋める。
5. **画面の確認（WO 冒頭が「画面変更: あり」なら必須。検証方針の SS-n）**:
   - **デモ表示モード**でログインし、内蔵ブラウザで変更した画面を撮影する。スマホ幅 375px は必須、PC 幅は WO で指定された画面のみ。
     ログインは**オーナーが内蔵ブラウザで行う**（実装役はパスワード等を入力しない）。ログイン画面を開き、「デモ表示モードにチェックしてログインしてください」とオーナーに頼む。
     内蔵ブラウザが `localhost` を開けない（denied 等）ときは、ブラウザのペインを表示して開き直し、オーナーに「localhost:3000 の許可を出してください」と頼む。
     頼み方: **作業役**は待たずに、report の冒頭の状態を「オーナー待ち: ◯◯（ログイン／localhost の許可）」にして止まる（仕様の穴ではないので、仕様の判断は求めない）。
     **別スレ**はオーナーに直接頼んで待つ（停止扱いにしない）。
     ログイン済みかどうかを `127.0.0.1` など別の宛先で確かめない（ログインの状態が残っていて本番の画面に移ることがある。2026-10-14 WO-009 の受入時）。
     本番データ・実在地名を写さない（LP 素材に流用するため。CLAUDE.md の方針）。
   - 撮った画面を S-n と見比べ、差分があれば**自分で直して撮り直す**。見比べた結果（S-n ごとに一致／直した内容）を report に書く。
   - 保存先: `docs/screenshots/WO-nnn/<画面>-<mobile|pc>.png`。
   - 保存の方法（WO-007 で使った方法）: 内蔵ブラウザで `screenshot` を撮ると、画像が
     `~/.claude/projects/<このプロジェクト>/<このスレのセッションID>/tool-results/mcp-Claude_Browser-blob-*.jpg` に残る。
     作業役のときは置き場所が違うことがある（確かめていない）。見つからなければ `~/.claude/projects/<このプロジェクト>/` の下で `mcp-Claude_Browser-blob-*.jpg` のいちばん新しいものを探す。
     いちばん新しいファイルを PowerShell で PNG に変えて保存する:
     `Add-Type -AssemblyName System.Drawing; $i=[System.Drawing.Image]::FromFile("<jpg>"); $i.Save("<保存先.png>",[System.Drawing.Imaging.ImageFormat]::Png); $i.Dispose()`
   - 画面をファイルとして保存できなかった場合は、無理に別の道具を入れず、その旨を report と中継文の「判断してほしい点」に書く。
6. `WO-nnn-report.md` に報告を書く（WO の「報告」欄の項目）。
7. **コードレビュー（軽量コースでも省略しない）**。
   - **作業役**: 自分では起動しない。report の冒頭の状態を「レビュー待ち」にして止まる。PM が批判役を起動し、指摘が report に書かれたら、PM から「対応して」と続きが来る（手順8へ）。
   - **別スレ**: サブエージェントを**モデル Opus** で起動し、次の文を**そのまま**渡す。
   補足・絞り込み・「ここは問題ない」等の誘導を**一切加えない**（作った側の思い込みを批判役に移さないため）。
   > `work-orders/ROLE-reviewer.md` を読んで、WO-nnn の「コードレビュー」をしてください。
8. **修正ループ**: 指摘（report 末尾の R-n）の分類で扱いを変える。
   - 【実装の不備】→ 直す。
   - 【テストの穴】→ **まず失敗するテストを足してから**直す。
   - 【仕様の穴】→ **直さない**。report の「PM に判断を求める点」に書いて**止まる**（仕様は PM とオーナーが持つ）。
   - 対応内容を R-n ごとに report に追記し、手順7に戻る（作業役は「レビュー待ち」で止まる／別スレは再度起動する）。画面に関わる修正をしたら手順5も撮り直す。
   - 重要度「高・中」が無くなったら終了。**レビューは最大3回**。3回で収束しなければ止まって PM へ。
   - 「低」の指摘は、直すか見送るかを report に理由付きで書く（受入の判断は PM）。
9. **報告して止まる**。report 冒頭の状態を「受入待ち」（途中で止まるなら「停止」「オーナー待ち」「レビュー待ち」）にする。
   **作業役**は、PM に要約だけを返す（状態・tsc/lint/test・スクショの枚数・判断してほしい点）。中継文は要らない。コミットも push もしない。
   **別スレ**は、PM に貼る中継文を
   **コードブロック1つ**で出す（オーナーがコピーボタン1回で全部コピーできるように）。説明はコードブロックの外に書く。
   **コミットも push もしない**（受入後に PM がする。本番反映もオーナーの指示で PM が行う）。形式:
   ```
   【中継】WO-nnn 完了報告
   - 報告ファイル: work-orders/WO-nnn-report.md（見る箇所: 「S-n/E-n の達成状況」「レビュー指摘」「PM に判断を求める点」）
   - 確認済み: tsc / lint / test 通過、コードレビュー n回で収束（高・中なし）、スクショ n枚（無ければ「画面変更なし」）
   - 判断してほしい点:
     1. …
     （無ければ「なし」）
   ```
   途中で止まる場合（仕様の穴・レビュー3回で収束しない 等）は1行目を「【中継】WO-nnn 停止（理由）」にする。

## 自分で決めてよい範囲
- 仕様を満たすための実装の細部（関数の分け方、命名、コンポーネント構成）。
- 既存のイディオム・コンポーネントの流用（`src/components/ui/*`, 既存の data 層関数など）。
- 明らかな書き方の改善（ただし範囲外の大きなリファクタはしない＝別 WO）。
- 純粋なロジック（計算・判定）を、テストしやすいように画面や DB から切り出すこと。

## PM に上げるもの（勝手に決めない）
- 仕様の解釈が割れるとき。**仕様の穴**（S-n／E-n に書かれていない振る舞い）に気づいたとき。
- 要件に無い機能を足したくなったとき（＝足さずに提案する）。
- DB スキーマの変更内容（`db-change` に従うが、何を足すかは仕様に書かれた範囲だけ）。
- 既存の設計判断（CLAUDE.md の「勝手に変えないでほしい方針」）に触れる変更。
- 本番データ・本番環境に影響する操作。

## 触ってよい / 触らないファイル
- 可: WO で指定された範囲、`work-orders/WO-nnn-report.md`（新規・追記）、`docs/テスト仕様書.md`（WO で指示された行の追加・結果記入）、
  `docs/screenshots/WO-nnn/`（スクショの保存）。
- 不可: `CLAUDE.md`（現在地は PM が更新）、`docs/変更管理表.md`（PM が記録）、WO の仕様本文、`.env*`、WO の範囲外のコード。

## 守ること（チラトラ共通）
- `~/.claude/CLAUDE.md` の共通規約（人が読める／根拠を添える／**要件外を良かれで足さない**）。
- DB は `db-change` スキル。**public と demo の両スキーマに当てる**。破壊的 SQL は `begin; … rollback;` で予行演習＋戻し SQL。
- 不変条件は仕様に「DB でも守る」とあれば CHECK 制約等で守る。
- `next dev` 中に `next build` をしない。`select *` を使わない。物理削除をしない（論理削除）。
- 自動テストから本番 Supabase に接続しない（テストは純粋なロジックに限る）。
- 秘密情報（service_role 等）を扱わない・クライアントに出さない。

## 起動の文
- 作業役（PM が起動）: `README.md` の「サブエージェント起動の固定文」の「実装役の起動」。
- 別スレ（オーナーが貼る）:
  > `work-orders/WO-nnn-<slug>.md` と `work-orders/ROLE-implementer.md` を読んで作業し、報告を `work-orders/WO-nnn-report.md` に書いて止まってください。
