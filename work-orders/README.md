# work-orders — チーム運用（役割分担）の進め方

このフォルダは、チラトラの開発を**ひとりでも"チーム開発の作法"で回す**ための仕組み。
`restoration-reform-research` の work-order 方式を、アプリの機能追加向けに翻訳したもの。
2026-10-09 から **VSDD（Verified Spec-Driven Development）をチラトラ向けに縮めて**取り入れている（下記）。

**原則: 各ファイルが自己完結する。スレ（セッション）を立て直しても・別フォルダから開いても・
サブエージェントに渡しても、同じ状態から再開できるように書く。会話履歴ではなくファイルを正とする。**

## 役割（ロール）

| 役割 | VSDD での呼び名 | 誰が | 何をするか | ファイル |
|---|---|---|---|---|
| **オーナー** | Architect | ユーザー本人 | 仕様の**承認**／論点の裁定／最終の受入 | — |
| **PM** | （進行役） | 本体スレ（CLAUDE.md を把握している） | 仕様・受入基準を書いて WO を起票／差し戻し先の振り分け／受入（関所）の判定案を作る／`CLAUDE.md`・`docs/変更管理表.md` を更新する。**コードは触らない** | （専用ファイルなし＝本体スレ） |
| **実装** | Builder | 作業スレ | テストを先に書く → 実装 → 報告して**止まる**。仕様の外は触らない | `ROLE-implementer.md` |
| **批判役** | Adversary | **毎回まっさらな別スレ**（＋コードは `/code-review` も併用） | 仕様の穴・実装の穴を突く。直さない | `ROLE-reviewer.md` |

PM・実装・批判役を**別々のスレ**で回す。批判役は**前の文脈を引き継がない**ことに意味がある
（同じスレで回すと、書いた側の思い込みを共有してしまい穴が見えなくなる）。

## VSDD の流れ（チラトラ版）

```
① 仕様化      PM: WO の「仕様」欄を書く（S-n 仕様項目 / E-n 境界ケース / 検証方針）
                 ↓
② 仕様レビュー  批判役(新スレ): 仕様の穴を突く → PM が直す …を繰り返す
   [関所1]      オーナーが仕様を承認するまで実装に渡さない   ← 手戻り防止の本丸
                 ↓
③ テスト先行   実装: 自動テスト（Vitest）を先に書き、全部「失敗」することを確認（Red Gate）
                       手動確認の項目は docs/テスト仕様書.md に先に行を足す
④ 実装         実装: テストを1本ずつ通す → リファクタ → tsc / lint / test を通す → 報告して止まる
                 ↓
⑤ 敵対的レビュー 批判役(新スレ) + /code-review: 仕様との一致・テストの質・実装・仕様の穴
                 ↓
⑥ 差し戻し     PM が振り分ける:
                 仕様の穴   → ①へ（WO を改訂。変更点を WO に記録）
                 テストの穴 → ③へ（境界ケース E-n を追加し、失敗するテストから）
                 実装の不備 → ④へ
                 ↓（⑤⑥を指摘が収束するまで）
⑦ 収束・受入   [関所2] PM が判定案 → オーナーが受入
                 → WO を「受入」に。変更管理表に記録。CLAUDE.md の現在地を更新
```

### 収束の基準（いつ止めるか）
- **仕様**: 批判役の指摘が「言い回し」だけになり、振る舞い・曖昧さ・検証漏れの指摘が出ない。
- **テスト**: 仕様項目 S-n・境界ケース E-n のすべてに対応するテスト（自動 or テスト仕様書の行）がある。
- **実装**: 批判役が重要度「高・中」の指摘を出せない（「低」だけなら PM 判断で受入可）。
- **検証**: `npx tsc --noEmit` / `npm run lint` / `npm test` が通る。DB 変更があれば下記「形式検証の代わり」も済み。

### 形式検証の代わり（原典の Phase 5 をチラトラ向けに置き換え）
原典は Kani / Dafny / TLA+ 等による証明を求めるが、チラトラ（Next.js + Supabase の業務アプリ）には過剰なので採らない。代わりに:
- **不変条件は DB の CHECK 制約・NOT NULL でも守る**（例: 残部 ≤ 持参）。アプリの検証だけに頼らない。
- **RLS の確認**: 追加したテーブル/ビューが anon で拒否されること（テスト仕様書 A-04 の手順）。
- **public / demo のドリフト確認**: 両スキーマに同じ DDL が当たっていること。
- 型・lint・自動テストが通ること。

### 規模による使い分け（PM が起票時に決め、WO に書く）
- **フル**: 新機能・DB 変更・業務ルールが増えるもの。①〜⑦すべて。
- **軽量**: 文言修正・小さな改善・基盤整備。①（仕様欄は短くてよい）→ ④ → ⑤（`/code-review` のみ可）→ ⑦。
  仕様レビュー（②）とテスト先行（③）は省略可。ただし受入基準を先に書く点は変えない。

### 追跡（トレーサビリティ）
原典の課題管理ツール（Chainlink）は使わず、**WO 内の ID の連鎖**で代用する:
`S-n（仕様項目）/ E-n（境界ケース）` → `テスト（テスト名 or テスト仕様書 No.）` → `実装（ファイル）` → `レビュー指摘（R-n）`。
テスト名・テスト仕様書の行には対応する `S-n` / `E-n` を書く。

## ファイルの決まり

- **WO ファイル**: `WO-<連番3桁>-<短いslug>.md`。`WO-TEMPLATE.md` をコピーして作る。
- **報告ファイル**: `WO-<連番>-report.md`。実装スレが書き、批判役が「レビュー指摘」を追記する。
- **状態**は WO 冒頭に書く: `起票` → `仕様レビュー中` → `仕様承認` → `作業中` → `レビュー中` → `受入` / `保留`。
  （軽量コースは `仕様レビュー中`・`仕様承認` を飛ばしてよい）
- **「真実の所在」**: 仕様・現在地は `CLAUDE.md`、変更の記録は `docs/変更管理表.md`、不具合は `docs/バグ管理表.md`。
  work-orders は「作業の単位と受入の記録」。重複させず、リンクで繋ぐ。

## スレを始めるときに貼る一文（コピー用）

- 仕様レビュー（批判役・新スレ）: `work-orders/ROLE-reviewer.md を読んで、WO-nnn の「仕様レビュー」をしてください。`
- 実装スレ: `work-orders/WO-nnn-<slug>.md と work-orders/ROLE-implementer.md を読んで作業し、報告を WO-nnn-report.md に書いて止まってください。`
- コードレビュー（批判役・新スレ）: `work-orders/ROLE-reviewer.md を読んで、WO-nnn の「コードレビュー」をしてください。`
