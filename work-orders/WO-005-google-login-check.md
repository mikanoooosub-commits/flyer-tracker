# WO-005: Google ログインの事前検証（本番プロジェクト・ローカルだけで試す）
- 作成日: 2026-10-13 / 作成: PM / 状態: **起票**（オーナーの準備待ち）
- コース: **軽量**（検証のみ。コードは残さない＝コミットしない。そのためコードレビューは対象外とする〔PM 判断〕）
- 画面変更: なし（ローカルで一時的にボタンを付けるだけ。本番には出さない）
- 背景: Google ログインを足す（WO-006 で実装予定）前に、Supabase の公式ドキュメントでは確かめきれない点を実地で確かめる。
  大前提（合意済み）: **アカウントの発行権はこちらが持つ**。Google は日々のログイン手段にすぎず、**未登録の Google アカウントは入れない**。

## 前提の確認（1-0。2026-10-13 オーナーと確認済み）
- 利用者は**オーナー1人**。チラトラの有効なアカウントは、オーナーの Gmail 1つだけ（メールアドレスは Google アカウントと同じ）。
- 既存のログイン方法（メール＋パスワード、メールリンク）は**残し、Google を足す**（WO-006）。
- 検証は**本番の Supabase プロジェクト**で行う（オーナー判断）。未登録側の試験には**オーナーのサブの Gmail**を使う。
  入れてしまっても見えるのはオーナー本人だけで、利用者が他にいないため危険はほぼ無い。
- 試すのは**ローカル（`npm run dev`）だけ**。本番の画面には Google のボタンを出さない。

## 公式ドキュメントで分かっていること（2026-10-13 PM 調査）
- 同じメールアドレス（確認済み）の既存ユーザーには、OAuth のログインが**既定で自動的に紐づく**（Identity Linking。https://supabase.com/docs/guides/auth/auth-identity-linking ）。
- 「Allow new users to sign up」を無効にすると「既存ユーザーしかサインインできない」とある（https://supabase.com/docs/guides/auth/general-configuration ）。ただし **OAuth に効くとは明記されていない** → T-1 で確かめる。
- 手動で別アカウントを紐づける機能（Manual linking）は既定で無効。セキュリティ上の報告があるため**無効のまま**にする。

## 確かめること（検証項目）
| ID | 試すこと | 期待 | 記録すること |
|---|---|---|---|
| T-1 | **サブの Gmail（未登録）**で Google ログイン | **拒否される**（ログインできない） | 画面の挙動（どこに戻るか、エラーの表示）、戻り先 URL のエラー（`error`・`error_description` 等。メールアドレスは書かない）、ユーザー数が増えていないこと（読むだけの SQL で件数） |
| T-2 | **オーナーの Gmail（登録済み）**で Google ログイン | 既存のアカウントでログインでき、いつものデータが見える | ユーザー ID が変わらないこと、そのユーザーに Google の identity が追加されたこと（読むだけの SQL。ID やメールアドレスの値は report に書かず「変わらない／追加された」で書く） |
| T-3 | T-2 の後、メール＋パスワードでログイン | 今までどおりログインできる | 結果 |

| T-5 | Supabase の設定の確認（読むだけ） | 「Allow new users to sign up」が無効、Manual linking が無効 | 画面で見た設定の状態 |

## T-1 で入れてしまった場合（中止の手順）
1. その場で検証を止め、オーナーが Supabase の画面で **Google ログインを無効に戻す**。
2. できてしまったユーザー（サブの Gmail）を消す。**完全削除なので、オーナーが実行**（README「DB の破壊的な操作の決まり」）。WO スレは対象を確かめる読むだけの SQL を用意する。
3. report に記録し、中継文で PM へ。WO-006 では「登録済みのメールアドレス以外はサーバー側で弾く」仕組みを必須にする。

## オーナーの準備（WO スレを立てる前。PM が内蔵ブラウザで手順を案内する）
1. **Google Cloud** で OAuth の設定を作る（オーナーの Google アカウントで操作）:
   - 同意画面は「外部」・**テスト**の状態にし、テストユーザーに**オーナーの Gmail とサブの Gmail の2つ**を登録する（テスト状態では、登録したアカウント以外は Google 側で入れない）。
   - OAuth クライアント（ウェブアプリ）を作り、承認済みのリダイレクト URI に Supabase のコールバック URL（`https://<プロジェクト>.supabase.co/auth/v1/callback`）を登録する。
2. **本番 Supabase** の Authentication で Google を有効にし、クライアント ID とシークレットを貼る（**シークレットはオーナーが貼る。チャットや文書に書かない**）。
3. Supabase の Redirect URLs に `http://localhost:3000/auth/confirm` が入っているか確かめる（メールリンクで使っているので入っている見込み）。
4. T-5 の設定（サインアップ無効・Manual linking 無効）を確かめる。
- 画面の名前や配置は Google・Supabase の更新で変わっていることがある。手順は当日の画面に合わせる。

## やること（WO スレ向け）
1. `npm run dev`（ローカル）。ログイン画面に**一時的に**「Google でログイン」ボタンを足す（`supabase.auth.signInWithOAuth({ provider: "google", options: { redirectTo: <origin>/auth/confirm } })`）。**このコードはコミットしない。**
2. オーナーに内蔵ブラウザで T-1〜T-4 を操作してもらう（Google のログイン画面での入力はオーナーが行う）。読むだけの SQL は WO スレが SQL Editor で流してよい。
3. 結果を `work-orders/WO-005-report.md` に書く。
4. 一時的な変更を元に戻す（`git checkout -- <変更したファイル>`）。`git status` で、report 以外に差分が無いことを確かめる。
5. 中継文をコードブロック1つで出して止まる。
