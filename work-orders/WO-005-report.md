## 各項目の詳細
### T-1 未登録（サブの Gmail）で Google ログイン
- Google の同意まで進んだ後、アプリの `/login` に戻った。ログインはできていない。
- 戻り先 URL: `/login?error=auth#error=access_denied&error_code=signup_disabled&error_description=Signups+not+allowed+for+this+instance`
  - 経路: Supabase → `/auth/confirm`（`code` なし）→ `route.ts` が `/login?error=auth` へリダイレクト。エラーの詳細は URL の**フラグメント（`#` 以降）**に付いている。
- 画面: ログイン画面に戻るだけで、**エラーメッセージは表示されない**（`login/page.tsx` は `?error=auth` も `#error=…` も読んでいない）。
- 読むだけ SQL（T-2 の後に実行。件数のみ）: `users_total = 1`、`users_created_last_24h = 0` → 新規ユーザーは作られていない。

### T-2 登録済み（メインの Gmail）で Google ログイン
- ログインでき、いつもの本番データが表示された（デモの帯は無し）。
- 読むだけ SQL の結果: `users_total=1 / identities_total=2 / identities_google=1 / identities_email=1 / users_with_both=1 / users_created_last_24h=0`
  - ユーザー数は変わらない（新規ユーザーなし）、同じユーザーに Google の identity が**追加された**（email と google の両方を持つユーザーが1）。
  - ユーザー ID の値そのものの比較は行っていない（「ユーザーが1人のまま、新規作成0、そのユーザーが両方の identity を持つ」ことで同一性を判断）。

### T-3 メール＋パスワード
- 今までどおりログインできた（オーナー報告）。

### T-4 デモにチェックして Google ログイン
- ログイン後、「デモデータを表示中」の帯と架空の学校が表示された。本番データは出なかった。
- 仕組み: デモのチェックを入れた時点で `demo_mode` cookie が付く。Google への往復をまたいでも cookie が残り、戻り先の `/auth/confirm` 以降も demo スキーマを参照した。
  → WO-006 で OAuth 側にデモ用の追加処理は**不要**（少なくとも同一ブラウザ・同一オリジンでは）。

### T-5 設定の確認
- 準備記録（2026-10-13）の「Allow new users to sign up」オフ・「Allow manual linking」オフを採用。今回の作業では画面の再確認はしていない。T-1 の `signup_disabled` が、サインアップ無効が効いている実挙動の証拠になる。

## WO-006 の仕様に効く気づき
1. **エラー時の画面**: 拒否されても画面には何も出ない。利用者から見ると「Google を押したら元に戻っただけ」。
   エラーの出し方（文言・どこで読むか）を仕様にする必要がある。
   - エラーはフラグメント（`#error=…&error_code=signup_disabled`）で届くため、**サーバーの `route.ts` では読めない**（ブラウザ側で読む必要がある）。
   - 現在の `route.ts` は `code` が無いと `/login?error=auth` に飛ばすだけで、元のエラー内容を捨てている。
   - 未登録で拒否された場合の文言は、既存のメールリンクの「このメールアドレスは登録されていません。管理者に招待を依頼してください。」と揃えるのが自然（提案。決めるのは PM／オーナー）。
2. **紐づけは自動**: 同じメールの既存ユーザーに Google の identity が追加された（Identity Linking の既定どおり）。仕様で「別ユーザーが増えない」ことを受入基準にできる。
3. **「登録済みメール以外はサーバー側で弾く」の必要性**: 今回は Supabase 側の設定（サインアップ無効）だけで拒否できた。
   ただし Google 側のテストユーザー制限（外部・テスト中）も同時に効いていた可能性がある。サブの Gmail は Google 側のテストユーザーに入っており（準備記録）、Google は通して Supabase が拒否した形なので、**Supabase 側の守りが単独で効いていることは確認できた**。
   Google を「本番公開」状態にする場合も、Supabase 側が守る前提を崩さないこと。
4. **デモ表示モード**: 上記 T-4 のとおり、cookie が往復をまたぐので追加実装は不要。デモ状態でログアウト→Google ログインでもデモのまま、という挙動が正しい。
5. **戻り先の許可 URL**: ポート 3000 固定。autoPort で別番号になると Google ログインが失敗する。ローカル検証・撮影の手順に注意書きが必要。
   今回は 3000 を別プロジェクトの dev サーバーが使っていたため、オーナーの了承を得て停止した（PID 停止。ほかの変更なし）。
6. 検証後の予定（PM が案内）: サブの Gmail を Google 側のテストユーザーから外す。
