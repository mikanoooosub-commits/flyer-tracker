  何が起きるか: 実在の可能性がある学校名（demo に紛れ込んでいた学校）が、コミット対象の文書に**名前そのまま**書かれている。スクショからは切り抜いて除いたのに、文書側で名前が残っており、ポートフォリオとして公開・画面共有したときに CLAUDE.md「実在地名・本番データをデモや画面共有に出さない」に触れる。

- R-3【低】【テストの穴】対象: `cooldown.test.ts` 「S-1: 名前の昇順（localeCompare ja）で並ぶ」
  何が起きるか: 期待値を実装と同じ `localeCompare(…, "ja")` で計算しているため、実装の比較式をなぞっているだけで、例えば比べる対象を取り違えても（前後空白の除去前の値で比べる等）期待値側も同じ並びになる場面がありうる。「何を入れても通る」までではないが、並びの期待値が人に読めない。
  直し方の案: 期待値を固定の配列で書く（例: `["あさひ通り", "正門前", "裏門"]` のように、実行して確定した並びを目で確かめて固定）。あわせて非推奨側（`excluded`）でも名前なしが末尾になることを1本足すと S-3(d) の「各々の並び順」を両側で突ける。

- R-4【低】【テストの穴】対象: `compareNewestFirst` の `created_at` 比較（E-12）
  何が起きるか: コメントのとおり文字列比較で正しく動く前提（PostgREST が `+00:00` の同じ形式で返す）だが、実際の値は小数秒の桁数が行によって違う（例: `…:00+00:00`／`…:00.5+00:00`／`…:00.123456+00:00`）。手元で確かめた限り、`+` < `.` < 数字 の文字順のおかげで正しく並ぶが、テストは小数秒なしの同一形式しか与えておらず、この前提が守られていることを誰も確かめていない。
  直し方の案: E-12 に小数秒の桁数が違う2件（例 `2026-08-01T01:00:00+00:00` と `2026-08-01T01:00:00.5+00:00`、`…00.12+00:00` と `…00.123456+00:00`）を足して、新しい方が先になることを固定する。

- R-5【低】【仕様の穴】対象: S-7（取得ループの失敗条件）
  何が起きるか: ページの合間に「1件追加」と「1件論理削除」が同時に起きると総件数は変わらず、`order(id)`＋オフセットのずれで1件を飛ばし別の1件を重複して取ったまま「成功」になる。仕様の失敗条件（総件数の変化・合計の不一致）では検出できない。発生は実績が 1000 件を超え、かつ数ミリ秒の間に2操作が重なるときだけなので現実的な確率は極めて低い。
  直し方の案: (a) 許容（仕様に「同時の追加＋削除は検出しない」と明記）／(b) 取得した行の `id` の重複を見つけたら取得失敗にする（`fetchAllRows` に id 取り出し関数を渡す形）。どちらにするかは PM が決める。
