# WO-004: クールダウンの日数を小学校マスタから変えられるようにする
- 作成日: 2026-10-12 / 作成: PM / 状態: **仕様承認**（2026-10-12 関所1 オーナー承認。仕様レビュー3回。実装は Opus を推奨）
- コース: **フル**（DB 変更あり）
- 画面変更: **あり**（小学校マスタ）
- 背景: WO-003 でクールダウンのしきい値（90日）をコードの定数1か所（`src/lib/cooldown.ts` の `COOLDOWN_DAYS`）にした（WO-003 の Q-3・Q-6、S-4）。
  オーナーは「基本は本部の指示の90日で変えないが、ハードコーディングが嫌い」。夏休みの前後に変えることがある。値をコードの外（DB）に出し、画面から変えられるようにする。

## 目的
- クールダウンの日数を、ログインしたメンバーが小学校マスタから変えられる。
- 今の日数が小学校マスタに常に見えている（夏休み明けの戻し忘れに気づける）。

## 仕様

### 前提の確認（1-0。2026-10-12 オーナーと確認済み）
- 数える単位: **日数は全校共通の1つの値**（学校ごと・立ち位置ごとには変えない）。
- 対象の範囲: 変えられるのは**クールダウンの日数だけ**（ほかの設定は作らない）。
- 変えられる人: **ログインしたメンバー全員**（既存の「相互に閲覧・編集」の方針どおり）。
- 表示する場所: **小学校マスタの中**。今の日数を**常に表示**し、そこから変更する。
- もらった具体例: 変えるのは夏休みの前後くらい。基本は本部の指示の90日で、変更はまれ。

### 用語
- **クールダウン日数**: WO-003 のしきい値 N。全校共通の1つの整数（単位: 日）。

### 仕様項目（S-n）
- **S-1**: 小学校マスタの**ページの先頭（追加フォームより上）**に「**クールダウン: {日数}日**」を常に表示する。横に「変更」ボタン（既存の `Button` の size="sm" 以上。学校の行の「編集」と同じ大きさ。小さい文字ボタンにしない）。
  学校が0校のときも表示する（開いてすぐ目に入れ、夏休み明けの戻し忘れに気づけるようにするため）。
- **S-2**: 「変更」でダイアログを開き、日数を入力して保存できる。入力欄の初期値は今の日数。範囲は **1〜365 の整数**（Q-1）。保存で閉じ、キャンセルで何も変えずに閉じる。
  **ダイアログを開くたびに**、入力欄を画面に表示中の日数に戻し、前回のエラー文を消す（保存後に開き直して古い値のまま保存し、黙って元に戻る事故を防ぐ）。
- **S-3**: 保存すると、小学校マスタのクールダウン判定（WO-003 の解禁日・クールダウン中／配布可）が新しい日数で計算し直される（画面を開き直さなくても、保存後の表示で反映）。
- **S-4**: 日数は DB に保存する。`src/lib/cooldown.ts` の定数 `COOLDOWN_DAYS` は廃止し、**コードに日数の値を書かない**（ハードコーディングしない）。
  WO-003 の判定関数は日数を引数で受け取る作りのままにし（今もそうなっている）、`page.tsx` が DB から読んだ値を渡す。
  DB の DDL に初期値 90 を書くのは可（SQL は運用の設定値を最初に入れる場所のため。Q-3）。
- **S-5**: 入力値はサーバー側で検証してから保存する（クライアントの検証だけに頼らない。共通規約）。検証は純粋な関数（`src/lib/cooldown-setting.ts`）で行い、次の順で判定する:
  1. 前後の空白（全角の空白を含む）を取り除く
  2. 全角数字 `０`〜`９` **だけ**を半角に直す（半角と全角が混ざっていてもよい）。丸数字・上付き数字などは直さない（文字全体を変換する正規化は使わない）
  3. 半角数字だけでできているかを見る（符号 `+`・`-`、小数点、指数 `e`、カンマ、単位「日」などが入っていればエラー）。先頭のゼロは受け付ける（「090」→ 90）
  4. 1〜365 の範囲かを見る
  検証関数は入力を**型の決まっていない値（`unknown`）として受け取り**、文字列でなければ（数値・null・未定義・配列など。Server Action はブラウザから任意の値を送れるため）同じエラーにする。
  検証で弾いたときのエラー文は1つにそろえる: 「**1〜365 の整数で入力してください**」。保存しない。
  画面側では事前の検証をしない（判定をサーバーの1か所にして、画面とサーバーで食い違わないようにするため）。
  範囲の 1・365 は**コードの定数1か所**（`cooldown-setting.ts`）と DB の CHECK に書く（Q-3。運用で変える値ではなく入力ミスを防ぐルールのため。S-4 の対象外）。
- **S-6**: 既存の小学校マスタの機能（追加・編集・位置・URL・削除、立ち位置の欄）の動きは変えない。
- **S-7**: 変更の記録（誰が・いつ・何日→何日）は**残さない**（Q-2）。表示するのは今の日数だけ。
- **S-8**: 保存は、更新した行が**ちょうど1行**であることを確かめる（Supabase は、対象の行が無い・RLS で見えないときもエラーを返さず0行の更新で成功扱いになるため。更新後の行を返させて数を見る）。
  1行でなければ、エラー文「**保存できませんでした。時間をおいてやり直してください**」を出し、保存できなかった扱いにする。想定外の DB エラーも同じ文にし、DB の生のエラー文は画面に出さない。
- **S-9**: 入力欄は `type="text"` ＋ `inputMode="numeric"` にする（数字のキーボードを出しつつ、全角数字などを消さずにサーバーへ送るため。`type="number"` は全角を空にしてしまうブラウザがある）。
- **S-10**: 保存に失敗したとき（検証で弾いた・S-8 の保存失敗）は、**ダイアログを閉じず**、ダイアログの中にエラー文を出し、**入力した値を残す**（直して保存し直せるように）。成功したときだけ閉じる。

### 前提・不変条件
- **DB 変更あり**。`db-change` スキルに従い、**public と demo の両方**に同じ DDL を当てる（demo は demo 用の値を持つ。デモで変えても本番に影響しない）。
  戻し SQL を用意し、**demo に先に当てて確かめてから** public に当てる。RLS は authenticated のみ・anon 不可。
- **本番に出す順番**: 新しいコードは DB からしか日数を読まないため、**public に DDL を当ててから**、コードを本番に出す（push）。
  戻すときは**コードを先に戻してから**戻し SQL を流す（逆にすると、本番で「クールダウンを表示できません」になる）。WO の受入後、本番反映（README 手順10）のときに PM が順番を確かめる。
- データ構造の案（最終決定は実装スレが `db-change` に沿って行い、report に理由を書く）: 設定を1行だけ持つテーブルを新設し、日数の列を持たせる。
  DDL で初期値 **90** の1行を入れる（public・demo とも）。**初期の行は「行が無いときだけ」入れる**（例 `on conflict do nothing`）。
  `schema.sql`・`schema_demo.sql` を流し直しても、画面から変えた値を上書きしない（夏休み中の 60 が黙って 90 に戻る事故を防ぐ）。
- 権限: Supabase は `public` に新しく作ったテーブルへ anon・authenticated の権限を既定で付けることがあるため、**先に `revoke all` で外してから**、authenticated に **`select, update` だけ**を grant する（public・demo とも）。
  RLS のポリシーも select・update だけを作る（insert・delete は無い）。行を追加・削除できるのは DB の管理者（SQL Editor）だけ。
- 1行の保証は、権限とは別に**制約でも守る**（例: 主キーが固定値しか取れない列にする。最終決定は実装スレ）。
- 不変条件（**DB でも守る**）: 日数は **1〜365 の整数**（CHECK 制約）、NOT NULL。設定の行は常に1行。
- 設定の行が読めない（無い・取得失敗）ときは、**黙って既定値を使わず**、エラー文「**クールダウンの日数を読み込めなかったため、クールダウンを表示できません**」を、**日数の行があるはずの位置（ページの先頭）**に出す。
  （実装の注意: 「設定だけ失敗」のときに WO-003 S-8 の文〔配布実績を…〕が出ないこと。失敗の原因ごとに文を出し分ける）コードに予備の値を持たない（S-4）。
  取得の失敗の組み合わせと表示:
  | 設定（日数） | 実績・立ち位置 | 日数の行と「変更」 | 各学校の立ち位置の欄 | エラー文 |
  |---|---|---|---|---|
  | 読めた | 読めた | 出す | 出す | なし |
  | 読めた | 失敗 | 出す（変更もできる） | 見出しごと出さない（WO-003 S-8） | WO-003 S-8 の文 |
  | 失敗 | 読めた | 出さない | 見出しごと出さない（日数が無いと判定できない） | 上の文 |
  | 失敗 | 失敗 | 出さない | 見出しごと出さない | 2つの文を並べて出す |
  学校の一覧と既存の機能（追加・編集・位置・URL・削除）は、どの場合もそのまま使える。
- 取得は列を指定する（`select *` を使わない）。

### 境界ケース（E-n）
- **E-1**: 1・365 → 保存できる。0・366・負の数 → エラーで保存しない。
- **E-2**: 「９０」「9０」（全角・混在）・「 90 」「　90　」（前後の空白）・「090」（先頭ゼロ）→ 90 として受け付ける。
  「90.5」「+90」「-0」「1e2」「9,0」「9 0」（数字の間の空白）「⑨⓪」（丸数字）「90日」「九十」・空・空白だけ・文字列でない値（数値の 90、null、未定義、配列）→ 「1〜365 の整数で入力してください」で保存しない。
- **E-3**: ダイアログの初期値と同じ値で保存 → 画面側で送信を省かず、**サーバーに保存を送り**、成功として閉じる（E-4 の後勝ちと矛盾させないため）。
- **E-4**: 2人がほぼ同時に別の値で保存 → 後から保存した値が残る（後勝ち）。それぞれの画面は、自分の**保存後の再表示**、または**ページを開き直したとき**に最新の値になる（ダイアログの初期値は、ページを表示したときの値）。
- **E-5**: デモ表示モード中に変更 → demo の値だけが変わり、本番（public）の値は変わらない。
- **E-6**: 設定の行が無い・読めない → エラー文、クールダウンの欄は出さない（既定値で表示しない）。
- **E-7**: 日数を変えた直後、解禁日が変わる（例: 前回 2026-10-12・90日 → 解禁日 2027-01-10。60日に変える → 2026-12-11）。
- **E-8**: 保存で更新した行が0行（行が無い・RLS で見えない）→ 「保存できませんでした。時間をおいてやり直してください」。
- **E-9**: DDL を流し直す → 画面から変えた値（例 60）がそのまま残る。

### 非機能
- スマホ 375px で「クールダウン: {日数}日」と「変更」が1行で読める。ダイアログの入力は数字のキーボードを出す（S-9）。
- RLS: 新しいテーブルは authenticated のみ（select・update。前提・不変条件の「権限」）。anon で拒否されることを確認する。
- デモ: スクショの前後で demo の値を変えた場合は、撮影後に **90 に戻す**（デモの見え方を変えないため）。

- R-1【仕様の穴】対象: 前提・不変条件「権限」・検証方針「不変条件（DB）③」
  何が問題か: Supabase のプロジェクトは、`public` スキーマに作ったテーブルへ **anon・authenticated に全権限（insert・delete を含む）を自動で付ける既定の設定**（default privileges）を持っているのが通常（今のプロジェクトの設定値は未確認。`schema.sql` に `revoke` は1つも無い）。

  直し方の案: 権限に「新しいテーブルは、まず anon・authenticated の権限をすべて外し（`revoke all ... from anon, authenticated`）、そのうえで authenticated に `select, update` だけを付ける。public・demo とも同じ」と書く。
  検証③に「`information_schema.role_table_grants` で、public・demo の両方について anon に権限が無く、authenticated は SELECT・UPDATE だけであることを確かめる」を足す。

- R-2【仕様の穴】対象: S-5・検証方針 S-5/E-1/E-2
  何が問題か: Server Action はブラウザから任意の値で呼べる（画面の作りに関係なく、文字列以外・null・数値・オブジェクトが届きうる）。S-5 の判定順は「文字列が来る」前提で、文字列でないものが来たときの扱いが無い。
  実装者が引数を `string` 型と宣言しただけだと、実行時には検査されず（型は消える）、`trim` で例外→想定外のエラー文、になりうる（共通規約「信用できない入力に `as`／型宣言だけで済ませない」）。
  直し方の案: S-5 の手順0として「文字列でなければエラー（『1〜365 の整数で入力してください』）」を足し、検証関数の引数は `unknown` で受けると書く。E-2 に「数値の 90・null・undefined（文字列でない）→ エラー」を足し、テストの入力にも加える。

- R-3【仕様の穴】対象: S-2・S-5・S-8（保存に失敗したときの画面）
  何が問題か: (1) 保存が失敗したとき（S-5 の検証エラー・S-8 の保存失敗）に、ダイアログを**閉じずに中にエラー文を出す**のか、閉じてページ側のエラー欄（既存の `error`。追加フォームの下）に出すのかが決まっていない。既存の学校の削除は「ダイアログを閉じてページ側に出す」作りなので、真似ると入力した値が消え、エラー文がダイアログの外（画面の下の方）に出る。
  (2) 失敗後に入力した値を残すか（「９０日」を直して再送できるか）が無い。
  (3) 画面側でも事前に検証するのかが無い。画面側で別の作り（例: 全角を受け付けない・`Number()` で判定）にすると、S-5 と結果が食い違う（画面で弾かれて E-2 の「９０」が通らない等）。
  直し方の案: 「失敗したときはダイアログを開いたまま、入力欄の下にエラー文を出し、入力した値は残す。保存中は保存ボタンを押せなくする」と S-2 に書く。画面側の事前検証は「しない（判定はサーバーの検証関数だけ）」か「同じ検証関数を使う」のどちらかに決めて書く（推奨: しない。判定の作りを1つにするため）。テスト仕様書の手動行に「全角で入力→保存できる」「90日と入力→ダイアログ内にエラー文、値が残る」を入れる。

- R-4【仕様の穴】対象: 検証方針 E-7・やること手順1（Red Gate）
  何が問題か: `getSpotStatus` は今も日数を引数で受け取る（`cooldown.ts`）ので、E-7 のテスト（日数 60 → 解禁日 2026-12-11）は**実装前から通る**。手順1の「自動テストを先に書き、全部失敗することを確認」と矛盾し、実装者が「Red にならない」と止まるか、Red に見せるためにテストを歪めるおそれがある。
  また E-7 のテストは関数の計算を確かめるだけで、確かめたいこと（**DB の日数が `page.tsx` から判定に渡ること**）は確かめられない（そこは S-3 の手動確認が担う）。
  直し方の案: 検証方針の E-7 に「既存の関数の振る舞いを確かめる回帰テストで、実装前から通る（Red Gate の対象外。report にそう書く）」と明記する。DB の値が判定に渡ることは S-3 の手動行（例: demo で 60 に変えて、テスト仕様書に書いた立ち位置の解禁日が E-7 の例どおり変わる）とコードレビュー（`page.tsx` が DB の値を渡し、予備の値を持たない）で確かめると書く。

- R-5【仕様の穴】対象: 前提・不変条件「取得の失敗の組み合わせと表示」（表）
  何が問題か: 設定が読めないときのエラー文「クールダウンの日数を読み込めなかったため…」を**どこに出すか**が無い。①日数の行の代わりにページの先頭（追加フォームより上）か、②既存の WO-003 S-8 の文と同じ位置（追加フォームの下）か。「2つの文を並べて出す」とあるので②とも読めるが、S-1 の「開いてすぐ目に入る」趣旨からは①とも読める。SS-1 にも失敗時の画面は無いので、実装者が決めることになる。
  あわせて、今のコードは「実績が読めない＝`spotsBySchool` が null＝S-8 の文を出す」作りなので、設定だけ失敗したときに立ち位置の欄を消す目的で同じ null を流用すると、**表の3行目で S-8 の文（配布実績を…）が誤って出る**。表は正しく書けているが、検証方針の E-6（コードレビュー）でこの点を見ることが書かれていない。
  直し方の案: 位置を1つに決めて表の下に書く（推奨: ①。日数の行があるはずの場所に出せば、戻し忘れの確認と同じ場所で異常に気づける。両方失敗のときは①に設定の文、②に S-8 の文）。検証方針の E-6 に「設定だけ失敗のとき S-8 の文が出ないこと」を足す。

- R-6【言い回し】対象: 仕様チェックリスト「スマホ幅 375px」・境界ケースの並び

- R-1【仕様の穴】対象: S-2・S-10・E-4（ダイアログを開き直したときの入力欄）
