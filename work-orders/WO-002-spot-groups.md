- 背景: クールダウン表示（WO-003）の検討中に、オーナーが数える単位を再裁定した（WO-003 の Q-1）。

  今のデータにはこの「配布ポイント」の情報が無いため、まず**配布ポイントを登録する仕組み**を作る（段階導入の1段目）。

## 中止の記録（2026-10-12）

- 理由: オーナーの具体例から、まとまりの中で非推奨でない立ち位置は「ほぼ1か所」と分かった。クールダウンは
  「**立ち位置ごと・最新の配布の評価が非推奨の立ち位置は対象外**」とすれば足り（WO-003 で実施）、まとまりの登録（DB 変更）は不要。
  共通規約「使うか分からない仕組みを先に作らない」にも沿う。
- **再開条件**: 同じ子どもが通る立ち位置で、評価が良好・普通のものが2か所以上ある（交互に使う等）ケースが運用で出てきたとき。
  その場合、片方で配ってももう片方が「配布可」と出て、90日以内に同じ子どもへ2回配る可能性がある。
- 再開時は本ファイルの仕様（「まとまり」版と「配布ポイント」版）とレビュー記録から続ける。
- 関連して見つかった別の候補: 同じ場所が別の立ち位置として二重登録されている場合の「立ち位置の統合」（履歴が分かれてクールダウンが正しく出ない）。

## 目的
- 小学校マスタで、学校ごとの配布ポイントと、ポイント外の立ち位置が見られる。
- 立ち位置を配布ポイントに入れる・外すことができる。WO-003 は配布ポイントを単位にクールダウンを数え、ポイント外の立ち位置は数えない。

## 仕様

### 用語
- **立ち位置**: 既存の `locations`（配布場所）のうち、小学校が設定されているもの。配布実績の登録や地図クリックで作られる（作られ方は変えない）。
  配布実績の有無にかかわらず全部を対象にする（Q-4）。同じ学校に同じ名前の立ち位置が複数あっても、そのまま別々に扱う（Q-5）。
- **配布ポイント**: 配る価値のある場所として登録した、立ち位置の束（Q-7・Q-9）。**同じ学校の中だけ**で作る（Q-1）。
  1つのポイントには立ち位置が**1つ以上**入る（目安は1〜2か所。上限は設けない）。**名前は付けない**（Q-2）。
  表示は所属する立ち位置名を「・」でつないだもの（例「西側」「東側角・東側歩道橋下」）。
- **ポイント外**: どの配布ポイントにも入っていない立ち位置。非推奨の場所として扱い、**配布実績の履歴は今どおり残すが、WO-003 のクールダウンでは数えない**（Q-9）。
- 1つの立ち位置は**多くとも1つ**の配布ポイントに入る。
- **並び順**: 立ち位置名を `localeCompare(a, b, "ja")` で比べた昇順。立ち位置名が空のものは**末尾**。同じ名前どうしは `id` の昇順。
  配布ポイントは、所属する立ち位置のうち並び順で先頭のものの順に並べる。

### 仕様項目（S-n）
- **S-1**: 小学校マスタの各学校のカードの中、**学校の行（名前・ボタン列）の下に、カードの幅いっぱいの欄**を出す（学校の行のボタン列・並びは変えない）。
  - 欄は**最初は畳んで**おき、見出し「配布ポイント（{ポイントの数}）」をタップすると開く。もう一度タップで畳む。開閉の状態は保存しない（Q-6）。
    操作（作る・加える・外す）をした後も、欄は開いたままにする。
  - 開くと、①配布ポイントを1行ずつ（並び順のとおり）、②その下に「ポイント外（{立ち位置の数}）」の見出しと、ポイント外の立ち位置を1行ずつ並べる。
  - 配布ポイントの行では、立ち位置名をそれぞれ小さな札（チップ）として並べ、各札に「×」（外す）を付ける。行の端に「加える」ボタン。
  - 立ち位置名が空（`spot` が空・null）の場合は「（立ち位置名なし）」と表示する。
  - 立ち位置が1つも無い学校は、見出しを「立ち位置なし」とし、開けないようにする（E-1）。
- **S-2**: **配布ポイントを作る**: 欄の中の「配布ポイントを作る」ボタンでダイアログを開き、その学校の**ポイント外**の立ち位置を**チェックボックスで1つ以上**選んで作る。
  ポイント外の立ち位置が無ければボタンを出さない。
- **S-3**: **加える**: 配布ポイントの行の「加える」ボタンでダイアログを開き、その学校の**ポイント外**の立ち位置を**チェックボックスで1つ以上**（複数可）選んで加える。
  ポイント外の立ち位置が無ければボタンを出さない。
- **S-4**: **外す**: 札の「×」で、その立ち位置を配布ポイントから外す（外した立ち位置はポイント外になる）。
  外すとポイントの立ち位置が0になる場合は、**確認ダイアログ**「この配布ポイントは無くなります。外しますか？」を挟む。
  「外す」でポイントは無くなり、「キャンセル」なら何も変えずにダイアログを閉じる。ポイントに立ち位置が残る場合は確認を挟まない（Q-8）。
- **S-5**: すでに配布ポイントに入っている立ち位置は、作る・加える操作の**選択肢に出さない**。別のポイントへ移すには先に外す（Q-3）。
- **S-6**: 操作の可否の判定（S-2〜S-5 の条件）は、画面や DB から切り離した**純粋な関数**で行い、画面の表示とサーバー側の処理（Server Action）の
  両方で同じ関数を使う。表示用の並び（S-1）を組み立てる処理も純粋な関数にする。
  - Server Action が受け取るのは **ID だけ**。作る＝立ち位置 ID の配列、加える＝ポイント ID＋立ち位置 ID の配列、外す＝ポイント ID＋立ち位置 ID。
    受け取った ID は**UUID の形式を検証**する（依存パッケージは追加しない）。
  - 判定に使う現在の状態（各立ち位置の学校・所属ポイント）は、画面から送られた値を使わず、**サーバーで DB から読み直して**判定関数に渡す。
- **S-7**: 配布ポイントの情報は DB に保存し、ログイン済みのチーム全員が見られ、編集できる（既存の「相互に閲覧・編集」の方針どおり）。
- **S-8**: 既存の機能（小学校の追加・編集・位置・URL・削除、配布実績の登録・編集、地図、一覧）の動きは変えない。
- **S-9**: 作る・加える・外す（ポイントが無くなる場合を含む）は、それぞれ **DB 関数（plpgsql。`rpc` で呼ぶ）で1つのトランザクションとして**行う。
  - 関数の中で、対象の配布ポイント行（`id` の昇順）→ 立ち位置行（`id` の昇順）の**順でロック**し（すべての関数で同じ順。デッドロックを防ぐ）、
    **ロックした後に状態を読み直して**検査する。条件に合わなければ**例外を出して何も変えない**（0行の更新を成功扱いにしない）。
  - 外して立ち位置が0になったポイントの行は、関数の中で削除する（先に立ち位置側の参照を NULL にしてから）。
  - 各スキーマの関数は**自スキーマのテーブルだけ**を参照する（テーブル名をスキーマ名で修飾する。demo の関数が public を書き換えないため）。
    public 版と demo 版の定義の差はスキーマ名だけにする。関数は呼び出したユーザーの権限で動く（RLS を効かせる）。
  - 関数の実行権限は `PUBLIC`／anon から外し、**authenticated にだけ**付ける（PostgreSQL は既定で `PUBLIC` に実行権限が付くため）。
- **S-10**: エラー文は次の3つにそろえる（どこで弾かれても同じ状況なら同じ文言）。
  - 他の人の操作が先に済んでいて条件に合わない（S-6 の判定で弾いた場合も、DB 関数の例外の場合も）: 「**他の人が先に変更しました。画面を更新してください**」
  - 要求の形式・内容が不正（UUID でない・空・重複・別の学校の立ち位置・学校未設定の立ち位置 等。画面が古いことでは起きないもの）: 「**操作を受け付けられませんでした。画面を更新してください**」
  - 想定外のエラー: 「**保存できませんでした。時間をおいてやり直してください**」（DB の生のエラー文は画面に出さず、サーバーのログにだけ残す）
  - 表示位置は既存の小学校マスタのエラー表示に合わせる。

### 前提・不変条件
- **DB 変更あり**。`db-change` スキルに従い、**public と demo の両方**に同じ DDL・DB 関数を当てる（`schema.sql`・`schema_demo.sql` を冪等に更新）。
  戻し SQL を用意し、破壊的な操作は `begin; … rollback;` で予行演習する。**demo に先に当てて確かめてから** public に当てる。RLS は authenticated のみ・anon 不可。
- データ構造の案（最終決定は実装スレが `db-change` に沿って行い、report に理由を書く）:
  配布ポイントのテーブル（学校への参照を持つ）を新設し、`locations` に配布ポイントへの参照列（NULL 可＝ポイント外）を追加する。
  既存の行はすべて NULL（＝ポイント外）で始まる。
- 不変条件（**DB でも守る**）:
  - 配布ポイントに入る立ち位置は、ポイントと**同じ学校**のものに限る。小学校が未設定（`school_id` が null）の立ち位置は入れない。
  - 1つの立ち位置は多くとも1つの配布ポイントに入る。
  - DB の制約の落とし穴（最終決定は実装スレ）: 複合外部キーに素の `on delete set null` を使うと `school_id` まで NULL になる（使わない）。
    複合外部キーは既定（`MATCH SIMPLE`）だと NULL を含む行を検査しないので、`MATCH FULL` にするか `check (ポイント参照 is null or school_id is not null)` を足す。
- 不変条件（DB 関数で守る）: 立ち位置が0の配布ポイントは残さない（S-9）。それでも残った場合は、画面に出さず、WO-003 でも数えない（E-12）。
- 配布ポイント → 学校の参照は、学校が削除されたら**ポイントも消える**（`on delete cascade`）。学校は紐づく立ち位置が無いときだけ削除できる（今どおり）ので、
  そのとき残りうるのは立ち位置0のポイントだけ。学校の削除は今どおりに動く（E-7）。ポイントが無くなっても**立ち位置の `school_id` は変わらない**。
- ポイントの行の削除は物理削除でよい（配布実績ではなく、論理削除の方針の対象外。変更履歴も残さない＝範囲外）。
- 不変条件: 配布ポイントの変更で、配布実績（`visits`）・監査ログ（`visit_logs`）・ピンの色・地図・一覧は変わらない。
- 型: `Location` 型に配布ポイントへの参照列を足す（共通規約「DB の列を足したら型も更新」）。既存の取得関数（`locations(*)` を取るもの）は変更しない
  （新しい列が結果に載るだけで振る舞いは変わらない。`select *` の解消は範囲外）。
- 取得: 立ち位置と配布ポイントの取得は列を指定する（`select *` を使わない）。学校ごとに問い合わせない（まとめて取得する）。
  件数上限（Max rows）で黙って打ち切られないよう、総件数（`count: 'exact'`）を取り、**取得件数と一致しなければ取得失敗**とする。
  取得失敗のときは、学校の一覧と既存機能はそのまま使えるようにし、欄の代わりにエラー文
  「**立ち位置を読み込めなかったため、表示できません**」を一覧の上に出す（配布ポイントの操作は出さない）。

### 境界ケース（E-n）
- **E-1**: 立ち位置が1つも無い学校 → 見出し「立ち位置なし」、開けない。操作は出さない。
- **E-2**: 配布ポイントが0で、ポイント外の立ち位置だけある学校 → 見出し「配布ポイント（0）」。開くと「ポイント外」だけが並び、「配布ポイントを作る」が出る。
- **E-3**: 別の学校の立ち位置を混ぜて作る／加える要求 → 画面で選べない。サーバーに届いても「操作を受け付けられませんでした…」で拒否（S-10）。DB でも拒否される。
- **E-4**: すでに配布ポイントに入っている立ち位置を、作る・加えるに使う要求 → 画面の選択肢に出ない。サーバーに届いた場合、画面が古いことによるものなので「他の人が先に変更しました…」で拒否（Q-3）。
- **E-5**: 立ち位置2つのポイントから1つ外す → ポイントは1つで残る（確認なし）。立ち位置1つのポイントから外す → 確認ダイアログ→「外す」でポイントが無くなり、その立ち位置はポイント外になる。「キャンセル」なら何も変わらない。
- **E-6**: 小学校が未設定の立ち位置 → 小学校マスタには出ない。配布ポイントにも入れられない（DB でも拒否）。
- **E-7**: 学校を削除しようとする → 今どおり、紐づく立ち位置があれば削除不可（テスト仕様書 No.E-04）。立ち位置もポイントも消えない。
- **E-8**: デモ表示モード中 → demo スキーマの配布ポイントを編集する（本番に影響しない）。
- **E-9**: 2人が同時に、同じポイント外の立ち位置を別々の配布ポイントに入れようとする → 一方は成功し、もう一方は何も変わらず「他の人が先に変更しました…」。
- **E-10**: 立ち位置名が空の立ち位置 → 「（立ち位置名なし）」と表示し、並びは末尾。他と同じように操作できる。
- **E-11**: 配布実績が1件も無い・全部論理削除済みの立ち位置 → 他と同じように表示・操作できる（Q-4）。同じ学校に同じ名前の立ち位置が2つ → 両方をそのまま表示（`id` 順。Q-5）。
- **E-12**: DB に立ち位置0の配布ポイントの行が残っている → 画面に出さず、見出しの数にも数えない。
- **E-13**: 要求に同じ立ち位置 ID が重複している（[X, X]）、存在しない ID、空の要求 → 拒否（「操作を受け付けられませんでした…」）。数は重複を除いて数える。
- **E-14**: 存在しない（または既に無くなった）配布ポイント ID への「加える」「外す」、そのポイントに入っていない立ち位置の「外す」 → 何も変えず「他の人が先に変更しました…」で拒否。
- **E-15**: 2人が同時に、立ち位置1つのポイントからその立ち位置を外す／そのポイントに別の立ち位置を加える → DB 関数のロックで順に処理される。
  後から処理された側は、条件に合わなければ何も変えず「他の人が先に変更しました…」。立ち位置0のポイントは残らない。

### 非機能
- スマホ（主）: 375px 幅で、欄の開閉・札・ダイアログが使え、立ち位置名が読める。PC でも同じ。
- RLS: 新しいテーブルは authenticated のみ（既存テーブルと同じ方針）。anon で拒否されること、DB 関数を anon で呼べないことを確認する。
- デモ: demo にも同じ DDL・DB 関数を当てる。demo のシードは各学校の立ち位置がちょうど2つ。スクショの前に、**デモ表示モードで**
  架空校のどれか1校で、立ち位置1つの配布ポイントを1つ作り、残りの1つはポイント外のままにする（「ポイント＋ポイント外」が写る）。
  別の1校では、立ち位置2つの配布ポイントを1つ作る（札が2つ並ぶ）。作ったポイントは**残す**（WO-003 の確認にも使う）。`seed_demo.sql` は変更しない。

### 範囲外（やらないこと）
- クールダウンの計算・表示（**WO-003**）。日数の設定画面（**WO-004**）。
- 立ち位置の名前の変更・統合・削除、立ち位置の新規作成画面（今どおり実績登録・地図から作る）。
- 地図・一覧への配布ポイントの表示。ポイント外の立ち位置を地図で目立たなくする等の表示変更。
- 学校をまたぐ配布ポイント（Q-1）。配布ポイントの名前（Q-2）。ポイントあたりの立ち位置数の上限。
- 同じ名前の立ち位置の区別・統合（Q-5）。実績の無い立ち位置の整理。配布ポイントの変更履歴（監査ログ）。
- ポイント外の立ち位置を、評価（非推奨）と自動で結び付けること（ポイントに入れるかどうかは人が決める）。

## 仕様レビュー指摘（第1回・2026-10-11）
批判役（サブエージェント）。根拠: 本WO、CLAUDE.md、`supabase/schema.sql`・`schema_demo.sql`・`seed_demo.sql`、`src/lib/types.ts`、`src/lib/data/queries.ts`・`actions.ts`、`src/components/schools/school-manager.tsx`、`docs/テスト仕様書.md`、WO-003。

- R-1【仕様の穴】対象: S-6・E-3・E-4
  何が問題か: 「サーバーでも同じ関数で判定する」とあるが、判定に使う**現在の状態（各立ち位置の学校・所属まとまり）をどこから取るか**が書かれていない。画面から送られた状態を判定関数に渡すと、改ざんされた要求も古い画面からの要求もそのまま通る（判定した意味がない）。
  直し方の案: 「Server Action は、受け取るのは ID だけ（立ち位置 ID の配列・まとまり ID）とし、判定に使う状態は**サーバーで DB から読み直して**判定関数に渡す」と S-6 に明記する。受け取った ID は zod 等で形式を検証する（共通規約「入力値はサーバー側で検証」）。

- R-2【仕様の穴】対象: 不変条件（2つ以上はアプリで守る）・S-2〜S-4・E-9
  何が問題か: 「作る」（まとまり行の insert＋立ち位置 N 行の update）、「外す→解消」（update＋残りの update＋まとまり行の delete）は複数の文になる。既存コードの Supabase クライアント（`supabase-js`）からは複数文を1トランザクションにできないため、途中失敗や同時操作で「立ち位置0〜1個のまとまり」が残りうる。例: 2個のまとまり {X,Y} から、Aさんが X を、Bさんが Y を同時に外す／Aさんが Z を加えるのと同時にBさんが X を外して解消する。E-9 は「同じ立ち位置を別のまとまりへ」の1パターンしか扱っていない。
  また、条件付き更新（`where group_id is null` 等）で負けた側は、PostgREST では**エラーにならず0行更新で返る**ため、「失敗してエラーを表示する」には0行を検出する作りが要る（書かれていない）。
  直し方の案（どれかを選んで明記）:
  (a) 作る・加える・外すを **DB 関数（plpgsql、`rpc` で呼ぶ）**にして、1トランザクション内でまとまり行をロック（`for update`）→検査→更新する。public・demo の両方に作る。
  (b) (a) をしない場合でも、**表示の組み立て関数（S-1）と WO-003 の数え方は「立ち位置が1個以下のまとまり」を単独として扱う**と決め、E-n（例: E-11「立ち位置が1個しかないまとまり行が DB に残っている → 単独として表示」）とテストを足す。
  あわせて「条件付き更新が0行なら失敗としてエラーを返す」を E-9 に書く。

- R-3【仕様の穴】対象: 前提（データ構造の案）・E-7
  何が問題か: (1) 解消時にまとまり行を物理削除するとき、`locations` 側の参照をどうするか（先に NULL にする／`on delete set null`）が未定義。DB の「同じ学校」不変条件を複合外部キー `(group_id, school_id) → groups(id, school_id)` で守る場合、素の `on delete set null` は **`school_id` まで NULL にしてしまう**（立ち位置が学校から外れる＝データ破損）。列指定の `on delete set null (group_id)`（PostgreSQL 15 以降の構文。本番 Supabase の版は未確認）か、アプリ／DB 関数で先に NULL にする必要がある。
  (2) まとまり→学校の外部キーの削除時の振る舞いが未定義。R-2 で立ち位置0個のまとまり行が残ると、`deleteSchoolAction` は `locations` しか数えないため削除に進み、`restrict` なら生の外部キーエラー文が出る（E-7「今どおり」から外れる）。
  直し方の案: 「まとまり→学校は `on delete cascade`（立ち位置が無い学校だけが消せるので、残るのは空のまとまりだけ）」または「`restrict` にして空のまとまりが残らないことを R-2(a) で保証する」のどちらかを明記。`locations` の参照の外し方も明記し、検証方針の DB 確認に「解消してもその立ち位置の `school_id` が残っている」ことを足す。

- R-4【仕様の穴】対象: 検証方針（不変条件（DB）, E-3, E-6）
  何が問題か: DB 確認が「別の学校の立ち位置・学校未設定の立ち位置をまとまりに入れる」だけで、**まとまりに入っている立ち位置の `school_id` を後から変える／NULL にする**更新が拒否されるかを確かめていない（今のアプリにその経路は無いが、DB で守ると書いた不変条件の片側）。
  直し方の案: 同じ `begin; … rollback;` の中で「まとまり所属の立ち位置の `school_id` を別の学校／NULL に update → エラー」も実行して report に記録する、と検証方針に足す。

- R-5【業務判断が要る】対象: S-1・用語「立ち位置」
  何が問題か: 小学校マスタに出す立ち位置の範囲が未定義。`locations` には、地図クリック（`createLocationAtAction`）で作ったが実績が1件も無いもの、実績が**すべて論理削除済み**のものも含まれる（作り間違いの残骸の可能性）。全部出すと一覧に使わない立ち位置が混ざり、まとまりにも入れられてしまう。WO-003 でもそれらを数えるかに波及する。
  直し方の案（オーナーが選ぶ）: (a) `school_id` がある立ち位置は実績の有無にかかわらず全部出す（今のデータの姿そのまま。単純） (b) 未削除の実績が1件以上ある立ち位置だけ出す (c) 全部出すが、実績なしのものに目印（例「実績なし」）を付ける。決めたら E-n（例: E-11 実績なしの立ち位置／E-12 実績がすべて論理削除済みの立ち位置）を足す。
